# XML Lifecycle Management

MAVLink definitions (messages, enums, and enum entries, including `MAV_CMD` commands) go through a lifecycle: they are proposed, accepted into the standard, and may later be replaced and eventually removed.
The XML file a definition is in, along with the [lifecycle elements](xml_schema.md#lifecycle-elements) it carries, show where it is in that lifecycle.
This lets implementers keep definitions that aren't ready out of their releases, and plan when to move away from old definitions.

## Lifecycle {#lifecycle}

1. **Proposed (WIP):** New definitions are added to [development.xml](../messages/development.md) and marked as [`<wip/>`](xml_schema.md#wip) (everything in this file is considered a work-in-progress but we tag anyway).
   New work-in-progress definitions that have to be added to common/standard/minimal (for some necessary reason) must also be marked as [`<wip/>`](xml_schema.md#wip).
   WIP definitions may change in incompatible ways and must not be used in released software.
2. **Accepted:** A definition moves to [common.xml](../messages/common.md) once it has been implemented in at least one core flight stack.
   Once in `common.xml` a definition is stable: any later change must be made compatibly, or by replacing it with a new definition.
3. **Standard:** A definition moves to [standard.xml](../messages/standard.md) once at least two key stakeholders use it compatibly.
4. **Superseded:** A definition is marked [`<superseded>`](xml_schema.md#superseded) when a newer definition better suits the use case.
   It is still fully supported, and no removal is planned.
5. **Deprecated:** A definition is marked [`<deprecated>`](xml_schema.md#deprecated) once the key MAVLink stakeholders have agreed a path for removal.
6. **Removed:** The definition is deleted from the XML.

::: info Review gates
In order for `<wip>` definitions to be accepted into the XML, at least one stakeholder must agree to support them (subject to testing) and another must be broadly supportive that the design is fit for purpose.
This same test is applied again before accepting definitions into common.xml and removing any `<wip>` tagging: reviewers may choose to reject or change definitions that they no longer consider fit for purpose.
:::

## Compile-Time Diagnostics (C/C++) {#diagnostics}

::: info
These diagnostics are only available in the C and C++ 11 libraries generated by _mavgen_.
They were added in [ArduPilot/pymavlink#1284](https://github.com/ArduPilot/pymavlink/pull/1284) (November 2026), and are present in libraries generated with a version of _mavgen_ that includes this change.
:::

The generated C and C++ 11 libraries can report, at compile time, where your code uses a definition marked `<wip>`, `<deprecated>`, or `<superseded>`.

Each flagged definition is tagged in the generated headers with a macro that does nothing by default.
If you define the macro as a compiler attribute (for example `deprecated` or `unavailable`), the compiler emits a warning or error wherever the definition is used.
Each category has its own macro, so you can choose how strict to be for each one.

| Category   | Typical use                                                                                                                                   |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| WIP        | Make any use an error in release builds, so that definitions that aren't ready can only be used in development builds.                        |
| Superseded | Usually leave this diagnostic off. Turn it on to find the code you need to upgrade to the `replaced_by` definition.                           |
| Deprecated | Warn, to find the code that still has to move to the replacement, and to confirm that nothing still uses the definition before it is removed. |

### Macros {#macros}

All of the macros default to empty, so a build that doesn't define any of them is unaffected.

| Macros                                                                                   | Applied to                                                                                                                                                    | Library                            |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| `MAVLINK_WIP`<br>`MAVLINK_DEPRECATED`<br>`MAVLINK_SUPERSEDED`                            | The C helper functions of a flagged message: `_pack()`, `_pack_chan()`, `_pack_status()`, `_encode*()`, `_send*()`, `_get_<field>()`, and `_decode()`.        | C (and C helpers used from C++ 11) |
| `MAVLINK_ENUM_WIP`<br>`MAVLINK_ENUM_DEPRECATED`<br>`MAVLINK_ENUM_SUPERSEDED`             | Flagged enum entries, including `MAV_CMD` commands. For a flagged enum: the enum type (the C `typedef` name, or the C++ `enum class`) and all of its entries. | C and C++ 11                       |
| `MAVLINK_MSG_TYPE_WIP`<br>`MAVLINK_MSG_TYPE_DEPRECATED`<br>`MAVLINK_MSG_TYPE_SUPERSEDED` | The message struct of a flagged message.                                                                                                                      | C++ 11                             |

An enum entry gets a macro for each of its own flags and for each flag on the enum declaration it came from.
A message gets just one macro: WIP, else deprecated, else superseded.

### How It Works {#how_it_works}

The generator writes the macro in front of each flagged declaration, for example:

```c
MAVLINK_WIP
static inline uint16_t mavlink_msg_command_cancel_pack(...)
```

By default the macro is empty, so this is an ordinary declaration.
If you `#define` the macro as a compiler attribute, the attribute is applied to the declaration, and the compiler reports any code that uses it.

The attributes are built into GCC and clang (see [GCC common attributes](https://gcc.gnu.org/onlinedocs/gcc/Common-Attributes.html) and the [Clang attribute reference](https://clang.llvm.org/docs/AttributeReference.html)).
The useful ones here are:

- `__attribute__((deprecated("text")))`: a **warning** (in the `-Wdeprecated-declarations` category) wherever the declaration is used.
- `__attribute__((unavailable("text")))`: an **error** wherever the declaration is used.
  This requires clang or GCC 12 or later.

The string is the message that the compiler prints with the diagnostic.

The attribute decides whether you get a warning or an error. Compiler flags can then change how warnings are treated:
`-Werror=deprecated-declarations` turns every `deprecated` warning into an error.
This flag applies to the whole compilation, not to a particular macro.

### Usage {#usage}

Define the macros before you include the dialect header (or pass them on the compiler command line).

#### C

```c
// Messages: use deprecated(), and add -Werror=deprecated-declarations to make it fatal.
#define MAVLINK_WIP              __attribute__((deprecated("MAVLink WIP message used")))
#define MAVLINK_DEPRECATED       __attribute__((deprecated("MAVLink deprecated message used")))
#define MAVLINK_SUPERSEDED       // leave empty: still fully supported

// Enum entries: unavailable() is a hard error, but needs clang or GCC >= 12.
#if defined(__clang__) || (defined(__GNUC__) && __GNUC__ >= 12)
#define MAVLINK_ENUM_WIP         __attribute__((unavailable("MAVLink WIP command/enum entry used")))
#else
#define MAVLINK_ENUM_WIP         __attribute__((deprecated("MAVLink WIP command/enum entry used")))
#endif
#define MAVLINK_ENUM_DEPRECATED  __attribute__((deprecated("MAVLink deprecated command/enum entry used")))
#define MAVLINK_ENUM_SUPERSEDED  // leave empty: still fully supported

#include <mavlink/common/mavlink.h>
```

Code that then uses a flagged definition is diagnosed like this (GCC):

```txt
warning: ‘mavlink_msg_protocol_version_pack’ is deprecated: MAVLink deprecated message used [-Wdeprecated-declarations]
error: ‘MAV_RESULT_NOT_IN_CONTROL’ is unavailable: MAVLink WIP command/enum entry used
```

A `deprecated(...)` attribute only produces a warning.
To make it an error, pass `-Werror=deprecated-declarations` to the compiler (GCC and clang):

```sh
gcc -Werror=deprecated-declarations ... -I generated/include ...
```

Or in CMake:

```cmake
target_compile_options(my_program PRIVATE -Werror=deprecated-declarations)
```

::: info
The flag turns every deprecated-declaration warning in the compiled files into an error, not just the MAVLink ones.
:::

#### C++ 11

The C++ 11 message structs use the `MAVLINK_MSG_TYPE_*` macros, while enum entries use the same `MAVLINK_ENUM_*` macros as C:

```cpp
#if defined(__clang__) || (defined(__GNUC__) && __GNUC__ >= 12)
#define MAVLINK_MSG_TYPE_WIP     __attribute__((unavailable("MAVLink WIP message used")))
#define MAVLINK_ENUM_WIP         __attribute__((unavailable("MAVLink WIP command/enum entry used")))
#else
#define MAVLINK_MSG_TYPE_WIP     __attribute__((deprecated("MAVLink WIP message used")))
#define MAVLINK_ENUM_WIP         __attribute__((deprecated("MAVLink WIP command/enum entry used")))
#endif
#define MAVLINK_MSG_TYPE_DEPRECATED  __attribute__((deprecated("MAVLink deprecated message used")))
#define MAVLINK_ENUM_DEPRECATED      __attribute__((deprecated("MAVLink deprecated command/enum entry used")))

#include <mavlink/common/common.hpp>
```

#### Release vs Development Builds

One way to apply this is to put the definitions in a project header that you include before the dialect header, and select them per build type.
Release builds then reject WIP usage, while a development or CI build reports deprecated usage for planning:

```c
#ifdef MY_PROJECT_RELEASE_BUILD
// Built with -Werror=deprecated-declarations: any WIP use fails the build
#define MAVLINK_WIP       __attribute__((deprecated("MAVLink WIP message used")))
#define MAVLINK_ENUM_WIP  __attribute__((deprecated("MAVLink WIP command/enum entry used")))
#else
// Warnings only: find code that needs to move off deprecated definitions
#define MAVLINK_DEPRECATED       __attribute__((deprecated("MAVLink deprecated message used")))
#define MAVLINK_ENUM_DEPRECATED  __attribute__((deprecated("MAVLink deprecated command/enum entry used")))
#endif
```

In CMake, for example, you can apply both to release builds only.
`target_compile_definitions()` defines `MY_PROJECT_RELEASE_BUILD`, which selects the macro definitions above, and `target_compile_options()` passes the flag that makes the `deprecated` warnings fatal:

```cmake
target_compile_definitions(my_program PRIVATE $<$<CONFIG:Release>:MY_PROJECT_RELEASE_BUILD>)
target_compile_options(my_program PRIVATE $<$<CONFIG:Release>:-Werror=deprecated-declarations>)
```

### Choosing an Attribute {#choosing_attribute}

::: warning

- Use `deprecated(...)` for the message function macros (`MAVLINK_WIP`, `MAVLINK_DEPRECATED`, `MAVLINK_SUPERSEDED`).
  `warning(...)` also fires inside the library's own code, because the generated functions call each other.
  `error(...)` only fires on calls that aren't inlined, so optimised builds usually miss it.
  `unavailable(...)` breaks `#include` under GCC.
- Only `deprecated(...)` and `unavailable(...)` are valid on enum entries and C++ structs.
  GCC's `warning(...)` and `error(...)` attributes apply only to functions.
- `unavailable(...)` needs clang or GCC 12 or later.
  Older GCC versions report "attribute directive ignored" for every flagged declaration, whether or not it's used, which breaks `-Werror` builds.
  Guard it as shown in the examples.
- With `-std=c++11` use the GNU `__attribute__((...))` form.
  The standard `[[deprecated]]` attribute needs C++14 on a struct and C++17 on an enum entry.

:::

### Limitations {#limitations}

A clean build does not prove that your code uses no flagged definitions:

- Message fields that hold enum values are plain integers, so setting or reading a flagged enum value through a message field isn't diagnosed.
- In C, the enum macro is applied to the `typedef` name, so `MAV_FOO x;` is diagnosed but `enum MAV_FOO x;` isn't.
- When an enum is extended in another XML file, each entry only carries the flags of the declaration it came from.
- The generated `<ENUM>_ENUM_END` marker is never flagged.

### Generated Test Suites {#test_suites}

The generated `testsuite.h` (C) and `gtestsuite.hpp` (C++ 11) use every message, including flagged ones.
They suppress the `deprecated` diagnostics they would otherwise trigger by wrapping those uses in `MAVLINK_DEPRECATED_CALL_BEGIN`/`MAVLINK_DEPRECATED_CALL_END` (diagnostic push/pop pragmas).
These also wrap the internal calls between the generated message functions.
If you override these macros, override both or neither.

A diagnostic pragma can't suppress `unavailable(...)`.
If you define `MAVLINK_MSG_TYPE_WIP` as `unavailable(...)` and build `gtestsuite.hpp`, also define `MAVLINK_TESTSUITE_SKIP_WIP` to skip the tests for WIP messages.
